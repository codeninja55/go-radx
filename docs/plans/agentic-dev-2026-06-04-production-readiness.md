# Production-readiness roadmap: conformant healthcare interoperability + the `radx` reference CLI

- Status: planning. This document is a roadmap; implementation proceeds increment-by-increment behind it.
- Date: 2026-06-04
- Goal: make go-radx a production-ready, conformance-tested-and-documented healthcare-interoperability
  library that can back a CLI and/or server for DIMSE, HL7 v2, FHIR R4/R5, and a DICOMweb client — with
  the reference `radx` CLI serving as a working example of every library feature and module.
- Scope: sequences the remaining milestones M3 (DIMSE depth), M4 (DICOMweb depth), M5 (HL7 v2 depth),
  M6 (FHIR generator, R4 + R5), M7 (convert depth, CLI, servers), and M8 (hardening, release) end to end.

## How this plan was produced

A multi-agent planning workflow ran eight parallel subsystem gap analyses (DIMSE, DICOMweb, HL7 v2,
FHIR R4/R5, convert, CLI/server, conformance-and-test infrastructure, and production hardening). Each
agent read the live code against its standard, reference doc, conformance statement, and the PRD. A
synthesis pass produced a draft roadmap, an adversarial completeness critic surfaced thirteen missing
areas, and a finalize pass folded them in. The result is the five-phase roadmap below: 64 work items,
each sized to a single reviewable increment, with an explicit acceptance criterion and the conformance
artifact (test or gate, plus the doc) that proves it.

## The `radx` reference-CLI mandate

`radx` is not a thin wrapper. It must be a working, runnable example of every library feature and module,
doubling as living documentation and an end-to-end smoke test of the public API surface. The coverage
obligation: every exported subsystem capability is reachable through a `radx` subcommand with a
documented, runnable example, and the end-to-end CLI tests exercise each one. Concretely this spans the
DICOM verbs (echo, store, find, get, move, scp, dump, modify, organize, lookup, catalogue), `hl7 send`
and `listen` over MLLP, `dicomweb wado`/`stow`/`qido`, the `convert` flows, and `serve` (the DIMSE SCP,
DICOMweb, FHIR REST, and MLLP server roles). It is built in Phase 3 and locked by readiness-checklist
item 12.

## How to read this plan

Phases are sequential and dependency-ordered. Phase 0 lays the cross-cutting conformance, safety, and
CI-hygiene gates that every later claim binds to. Phase 1 builds the FHIR generator, the highest-leverage
dependency. Phase 2 builds subsystem depth in parallel. Phase 3 productizes the CLI and servers. Phase 4
hardens and cuts v1. Within a phase, work proceeds increment-by-increment: a fresh subagent per
increment, TDD, a real interop or conformance gate, per-increment review, and a per-increment PR — the
established go-radx cadence. Nothing in this document is implemented yet. The Phase 0 work items are
tracked as the active task batch; later phases are tracked here until their phase begins.

## Roadmap

### Phase 0 — Conformance gates, supply-chain pinning, and CI-hygiene foundations

**Goal:** Lay every cross-cutting safety, observability, determinism, and verification gate that all later conformance claims bind to, and absorb the cheap-but-high-value gates the critique pulled earlier: wire the existing-but-unrun interop tests into CI, pin all reference tools and interop images so the heavy Phase 2 interop work runs against deterministic gates, bring the cmd/radx module into CI immediately so it cannot rot, make the conformance-drift check merge-blocking per-PR from day one, seed the DICOM Part-10/pixel fuzz targets and codec benchmark baseline (the largest untrusted-binary surface), establish a standing -race gate, and declare an honest v0.x pre-1.0 stability posture with governance docs. This phase builds gates and removes build-hygiene defects; feature work in later phases lands behind these merge-blocking gates from the first increment.

**Exit gate:** All Phase 0 gates green and merge-blocking in CI: zap is a direct, context-injected, PHI-aware logger with a no-PHI test; a library-wide PHI-default sanity sweep, a fuzz-in-CI harness (hang=failure) seeded with the DIMSE PDU and DICOM Part-10/pixel-reader targets, an 80% coverage floor, a standing -race gate, and a pinned merge-blocking govulncheck all run; the existing DICOMweb and convert e2e interop tests are wired into the CI interop matrix and green; all reference tools (FHIR validator, pydicom, pynetdicom, python-hl7, dicom3tools) and Orthanc + dcm4chee-arc interop image digests are pinned; the committed cmd/radx/radx binary is git-removed and gitignored; cmd/radx and root share the Go toolchain, a go.work ties the modules, and a minimal build+vet+lint+govulncheck CI matrix entry covers cmd/radx; a DICOM codec/Part-10 benchmark baseline is recorded; stub conformance statements for DICOMweb, DIMSE, convert, and CLI/server exist under docs/conformance/ with not-yet-shipped banners, the over-claiming HL7v2 and FHIR statements carry per-section status annotations, and the conformance-drift check (counts plus not-yet-shipped banners) is merge-blocking for every statement; SECURITY.md, CONTRIBUTING.md, CODE_OF_CONDUCT.md, and a v0.x pre-1.0 experimental stability banner exist; the mkdocs site builds with links verified.

### Phase 1 — FHIR R5 generator and models (M6a), the validator gate, and R4 bundle de-risking

**Goal:** Build the build-time FHIR code generator end to end (loader→model/IR→planner→emitter), extend the loader to capture filter-based value-set includes before the binding-enum increment depends on it, generate the full R5 5.0.0 resource and backbone set (including CapabilityStatement so the Phase 3 client/server capability path enters validated) with conformant choice-type, primitive-extension, required-binding, and Decimal handling, the identity API, the structural Validate engine, Bundle builders, and full JSON round-trip. Stand up the official HL7 FHIR validator as a merge-blocking CI gate over the workflow set. Vendor and checksum the R4 4.0.1 StructureDefinition bundle here (the Phase 2 R4 generate-rerun assumes it exists; the provenance/licensing review is the kind of supply-chain step that stalls a phase). Seed the first malformed FHIR corpus with provenance as the decode/validate fuzz targets land. This is the single highest-leverage dependency: convert depth, the FHIR REST client, and the FHIR server role are all blocked at the type level until these resources exist.

**Depends on:** Phase 0 — Conformance gates, supply-chain pinning, and CI-hygiene foundations

**Exit gate:** go generate ./fhir/... reproduces the committed R5 tree byte-for-byte (CI gate); the whole fhir/r5 package compiles; the loader captures filter-based ValueSetInclude.Filter; identity API, choice types, primitive extensions, required-binding enums (with a test proving no empty const set ships silently), CapabilityStatement, Bundle builders, the Validate engine, and canonical JSON round-trip with _summary modes are all tested; the official HL7 FHIR validator gate is merge-blocking and passes for the R5 workflow set (Patient, Encounter, ServiceRequest, ImagingStudy, DiagnosticReport, Observation, Bundle, OperationOutcome, CapabilityStatement) with a proven negative fixture; the R4 4.0.1 StructureDefinition bundle is vendored, checksummed (SHA256SUMS + SOURCE.md), and provenance-reviewed; convert and the M2 skeleton are migrated off the hand-written resources and green; the FHIR decode/validate paths are fuzzed in the Phase 0 harness (never panic, never leak PHI, truncation is io.ErrUnexpectedEOF) and a seeded malformed-FHIR corpus with provenance exists for the Phase 4 hostile-input gate; each FHIR conformance statement section is drift-checked in lockstep.

## Top risks

1. The FHIR generator is the long-pole single point of failure: convert depth, the FHIR REST client, and the FHIR server role are all blocked at the type level until R5 resources exist. A slip in the loader→IR→planner→emitter pipeline cascades across three subsystems, and the loader Filter-capture extension is a within-phase prerequisite for the binding-enum increment. Mitigation: prove the pipeline end-to-end on one representative resource (with the byte-for-byte diff gate) before bulk generation, land the loader Filter-capture before the binding increment, and keep the M2 skeleton green as the drop-in-superset regression.
2. The conformance and reference docs currently over-claim across HL7v2, FHIR, DICOMweb, and convert — they describe M4/M5/M6 end-states as if shipped. For medical-device-adjacent software a conformance statement asserting capability the code lacks is a safety hazard, and the enforcement window between a one-time Phase 0 annotation and a Phase 4 reconciliation would let statements drift back into over-claiming. Mitigation: Phase 0 adds honest not-yet-shipped banners AND makes the drift check (counts plus banners) merge-blocking per-PR from the start, so every later increment updates its statement in lockstep with the PR throughout the build-out.
3. The official HL7 FHIR validator gate is declared merge-blocking but does not exist anywhere in the repo, and the mechanism (validator_cli.jar vs container vs Inferno) is undecided. Until it lands, is pinned, and passes with a proven negative fixture, every FHIR/convert conformance claim is self-asserted. Mitigation: pin the validator mechanism in Phase 0 and treat validator-gate wiring (with a deliberately-invalid negative fixture) as a Phase 1 exit-blocking item, not an enhancement.
4. Interop determinism: the dcm4chee-arc stack (LDAP+PostgreSQL+WildFly) is memory-heavy and flaky, all reference tools and image digests are unpinned today, and Phase 2 adds seven new interop gates against exactly those stacks. Storage Commitment's separate-association N-EVENT-REPORT may not work against real dcm4chee. Mitigation: pin image digests and tool versions in Phase 0 (moved forward from Phase 4) so the heavy Phase 2 interop work runs against deterministic gates, and either implement the separate-association model or document it as a stated limitation rather than block on it.
5. Silent data-corruption in cross-standard mapping is the highest-consequence correctness risk and the hardest to see: the HL7 XCN-as-XPN defect already misreads provider identifiers today, convert has no validator gate or round-trip tests, and the new DIMSE retrieve services could launder partial failure into success. Mitigation: fix XCN before any converter consumes provider identity, gate every converter's output through the FHIR validator plus round-trip fidelity and determinism tests, and ship each new DIMSE service with a deliberate partial-failure interop fixture proving failure surfaces as failure.
6. The DICOM core's Part-10 dataset/pixel readers and 11 compressed fixtures are the single largest untrusted-binary attack surface and have zero fuzz coverage and no codec benchmark today, yet the memory note treats DICOM as 'done'. Mitigation: seed the DICOM Part-10/pixel fuzz targets and a codec/Part-10 benchmark baseline in Phase 0 (not folded into a single late line), and complete ASAN/UBSAN codec builds and the hostile-input gate in Phase 4.
7. The CLI and server are essentially greenfield (a stub main and a doc-only package) and cmd/radx is a separate module excluded from ./..., so it would rot undetected through Phases 1-2 while its toolchain is touched in Phase 0. The 0-5 exit-code taxonomy also rests on an unverified assumption that every subsystem's typed errors are classifiable. Mitigation: bring cmd/radx into CI with go.work and a minimal build+vet gate in Phase 0, and audit the cross-package typed-error inventory before wiring exit codes in Phase 3.
8. PHI leakage, transport security, and the hostile-input corpus are baseline medical-device requirements currently convention-enforced, not test-enforced: zap is unwired, there is no library-wide PHI sweep, DIMSE has no TLS, several parsers are unfuzzed, and no malformed corpus exists. Mitigation: Phase 0 makes the PHI sweep and fuzz harness merge-blocking from the start; the malformed corpus is seeded incrementally as each parser's fuzz target lands in Phases 1-2 so the Phase 4 hostile-input gate has a real corpus to run; DIMSE-TLS and full-parser fuzzing/ASAN are explicit Phase 4 exit-blockers.
